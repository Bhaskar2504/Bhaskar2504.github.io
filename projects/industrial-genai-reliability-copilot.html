Industrial GenAI Reliability Copilot

Turning industrial reliability reasoning into an evidence-grounded, testable and governed GenAI troubleshooting workflow.

Industrial troubleshooting requires more than a fluent answer. An engineer needs to know what evidence was used, which conclusions are only hypotheses, what contradicts the diagnosis, where uncertainty remains and when the system should stop and ask for human review.

This project demonstrates how those requirements can be designed into a GenAI application rather than added after the model has already generated an answer.

Current Capability

v0.3 — RAG and Citations

The project now retrieves traceable engineering evidence from a synthetic knowledge base before producing a structured diagnostic response.

The Problem

Why a reliability copilot needs stronger controls than a normal chatbot.

Diagnosis is evidence-dependent

The same symptom can have different explanations depending on operating state, measurement quality, system configuration and supporting signals.

Anomaly is not root cause

A statistically unusual pattern may deserve attention, but it does not by itself confirm a mechanical, electrical or process failure.

Fluent answers can still be unsafe

Engineering outputs must expose uncertainty, avoid unsupported claims and escalate when evidence is weak or the request is safety-sensitive.

Evaluation must be measurable

The application uses schemas, evidence IDs and reproducible test cases so quality can be checked systematically rather than judged only by writing style.

Architecture

From question to traceable engineering response.

01

Validate input

Check the engineering question and identify safety-sensitive requests.

02

Retrieve evidence

Search synthetic engineering notes using deterministic TF-IDF cosine retrieval.

03

Create evidence records

Attach stable evidence IDs, source titles, excerpts and source locators.

04

Generate structured output

Use a versioned reliability prompt and machine-validatable diagnostic schema.

05

Validate citations

Reject evidence IDs that were never retrieved or supplied to the model.

06

Apply guardrails

Abstain or escalate when evidence is missing or the request is safety-sensitive.

07

Record traces

Capture retrieval and validation events for later inspection.

08

Human engineer decides

The application supports diagnosis; it does not confirm root cause or execute plant actions.

What v0.3 Implements

RAG that can be inspected and tested.

Knowledge ingestion

Markdown engineering notes are converted into stable paragraph-level chunks. Only synthetic information is currently included.

Deterministic retrieval

A small TF-IDF cosine retriever provides a transparent baseline without requiring a hosted vector database or embedding API.

Traceable citations

Each retrieved chunk becomes an evidence record with an ID and locator such as knowledge/synthetic/...#chunk-001.

Prompt versioning

The active diagnostic prompt is versioned as diagnostic-v0.3, allowing behavioural changes to be traced across releases.

Structured engineering output

Hypotheses, evidence, confidence, recommended checks, abstention and escalation are returned as machine-validatable fields.

Safe failure behaviour

Unsupported citation IDs are rejected, missing evidence triggers abstention and safety-sensitive requests require qualified human review.

Evaluation

Published results include the failure.

The v0.3 evaluation uses seven targeted retrieval queries over the synthetic knowledge base. These numbers measure retrieval and citation mechanics, not real-world equipment diagnostic accuracy.

85.7%Retrieval precision@1
100%Citation-ID accuracy
100%Source-locator completeness
100%Repeated retrieval consistency

6 cases passed

Pump suction restriction, sensor disagreement, evidence quality, bearing vibration, boiler oxygen/draft and motor-current context were retrieved correctly at rank 1.

1 case deliberately failed

An ambiguous query containing both pump/flow and current language ranked the pump-suction document above the intended motor-current document. The failure remains visible because it exposes a real limitation of simple lexical retrieval.

Important: citation validation in v0.3 is structural. The application verifies that cited evidence IDs came from the retrieved set. It does not yet claim semantic entailment scoring for every generated sentence.

Safety & Governance

The system is designed as decision support.

Evidence boundaryGenerated hypotheses may cite only evidence records supplied to the diagnostic step.
AbstentionNo evidence should result in an explicit refusal to produce a grounded diagnosis.
EscalationSafety-sensitive requests are routed to qualified human review.
Prompt-injection treatmentRetrieved text is treated as untrusted evidence, not as instructions for the application.
ConfidentialityNo employer, customer, plant, alert-history or proprietary failure-mode information is used.
Engineering authorityThe application does not replace approved procedures, OEM guidance or qualified engineering judgement.

Research Direction

Adding a symbolic reasoning layer.

The current project uses retrieval, structured outputs and validation. A future extension is to evaluate whether explicit logic programming can strengthen failure-mode reasoning where hard rules, exclusions and traceability matter.

Current Limitations

What the project does not pretend to solve yet.

Small knowledge base

The current evidence corpus is intentionally small and synthetic. It is sufficient for testing architecture, not for broad industrial coverage.

Lexical retrieval

There is no embedding model, hybrid retriever or reranker yet. Ambiguous terminology can therefore produce incorrect ranking.

No semantic citation judge

The system validates citation identity and provenance, but does not yet score whether each cited chunk semantically proves every claim.

No engineering tool calling yet

Deterministic calculations and trend-analysis tools are deliberately reserved for v0.4.
