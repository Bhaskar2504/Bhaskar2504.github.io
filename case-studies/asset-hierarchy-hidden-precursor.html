EAM/APM Data Quality · Precursor Linkage

The warning was there. The asset hierarchy hid it.

A precursor and the later adverse event belonged to the same physical equipment—but structured location coding separated the records.

01 · What happened

Two records. One machine. Two different locations.

The structured data fragmented a sequence that was physically coherent.

Precursor
A fault indication is raised on an auxiliary rotating device.

The maintenance description identifies the equipment and the fault mechanism clearly enough to be useful.

Data issue
The precursor is booked under a neighboring or parent system rather than the asset's later event location.

A location-code query would put the record into the wrong reliability population.

Later event
The same physical device reaches a trip/protection event on the same fault family.

The later record is stored elsewhere in the hierarchy, so the precursor-to-event chain is not obvious.

Reconstruction
Maintenance text and equipment context reconnect the two records.

The combined sequence becomes usable for event review, hierarchy correction and future APM logic.

Information architecture

The database path and the physical asset are not always the same thing.

Asset hierarchy is a model of the plant. When that model is wrong, analytics inherit the error.

Naïve analytics

Trust structured location alone

  • Miss precursor linkage
  • Under-count recurrence
  • Train labels on fragmented history
  • Send engineers to the wrong asset population
Engineering-grade analytics

Reconcile hierarchy with physical context

  • Validate asset references in text
  • Use parent/child and neighboring-system logic
  • Deduplicate related work
  • Flag hierarchy defects for correction

Engineering interpretation

Information architecture hid a physically coherent sequence

The public conclusion is about data quality and event linkage—not proof that the precursor would certainly have prevented the later event.

1Confirm physical equipment identity from engineering documentation.
2Check parent/child functional-location logic and tagging rules.
3Rebuild the event population after hierarchy correction.
4Review whether similar cross-tag defects exist elsewhere.
APM implicationAsset hierarchy validation belongs upstream of predictive modelling.

If the event history is split across inconsistent identifiers, model labels, recurrence counts and RCA evidence will be wrong before the algorithm starts.

Scope: This case demonstrates that a precursor and later event can be separated by structured-data errors. It does not claim that the precursor guaranteed the later event or that correcting the hierarchy alone would prevent failure.
Public-safety statement. Composite case. Identifying organization, site, asset tags, exact time interval, transaction IDs, source-system name, costs and original maintenance wording are intentionally omitted.
